O bug que o TypeScript não avisa

sql`` do Drizzle: quando usar, e o gotcha do numeric que virou ::float no seu próprio código

Código real, de agora mesmo — server/database/queries/instalacao.ts: 

export async function buscarEstatisticasPeca(pecaId: string) {
  const [resultado] = await db
    .select({
      totalRegistros: sql<number>`count(*)::int`,
      notaMedia:      sql<number | null>`round(avg(${instalacao.nota}), 1)::float`,
      precoMedio:     sql<number | null>`round(avg(${instalacao.custo}), 2)::float`
    })
    .from(instalacao)
    .where(eq(instalacao.pecaId, pecaId))

  return resultado
}

1. Por que sql`` aqui, e não o query builder normal?

O query builder do Drizzle cobre select/where/ insert/join com segurança de tipo. Mas não tem método pronto pra avg(), count() ou aritmética de data — essas são expressões SQL que o builder não modela. Pra isso, o Drizzle dá o sql tagged template: um escape hatch que mistura referência de coluna tipada com SQL cru.

"sql template allows you to write more type-safe and parameterized queries" — e pode ser usado seletivamente dentro de um select, where, orderBy.

— documentação oficial do Drizzle

2. A interpolação não é concatenação de string

Quando você escreve sql`${instalacao.nota}`, o Drizzle não gruda texto — ele escapa o identificador da coluna ("instalacao"."nota") e, pra valores dinâmicos, gera parâmetro ($1) em vez de embutir o valor na string. É seguro contra SQL injection do mesmo jeito que o resto do query builder.

3. O gotcha: sql<T> não converte nada

Aqui está o ponto que essa lição quer que grude: sql<number> é só uma dica pro TypeScript. Em runtime, o valor que volta é o que o banco e o driver decidirem devolver — a anotação de tipo não muda nada de verdade.

Sem .mapWith(), não existe conversão automática. sql<number> é aviso de compilador, não garantia de runtime.

E aqui mora o motivo real do ::float e do ::int no seu código: colunas numeric (como custo) e o resultado de count(*) (tipo bigint) voltam como string do Postgres via postgres.js — de propósito, pra não perder precisão que o número de 64 bits do JavaScript não representa direito.

sem o cast, isso quebraria silenciosamente
sql<number>`avg(${instalacao.custo})` devolveria a string "200.00" — o TypeScript juraria que é number, mas precoMedio + 1 viraria "200.001", não 201.

O ::float e o ::int forçam o Postgres a devolver um tipo que o driver já sabe mapear pra número de verdade — integer comum não sofre disso, só numeric e bigint.

Pratique — recupere da memória, não releia

1. Por que a query usa sql`avg(...)` em vez de um método pronto do Drizzle?
Isso — avg/count/interval não têm método no builder. Não é regra geral nem questão de performance.
Não. O motivo é específico: essas funções não têm método no query builder, nada a ver com performance ou regra geral.
2. O que sql<number> faz, exatamente?
Exato — é aviso de compilador. Sem .mapWith(), zero efeito em runtime.
Não. sql<T> não converte nada — é só o que o TypeScript acredita, não o que acontece de verdade.
3. Por que count(*) e avg(custo) levam cast, mas uma coluna integer comum não precisa?
Isso — bigint (de count) e numeric (de custo) voltam como string por design, pra não perder precisão. integer não tem esse problema.
Não. É específico dos tipos bigint/numeric — não é regra geral de "toda agregação" nem do Drizzle.

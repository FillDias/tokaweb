Como o SeloCompat decide o que mostrar

<script setup>, defineProps e computed — a forma de todo componente do TOKA

Componente real, app/components/base/SeloCompat.vue — o mesmo que já roda na sua ficha de peça:

<script setup lang="ts">
type Estado = 'direto' | 'adaptacao' | 'nao_serve' | 'sem_dados'

const props = defineProps<{
  estado: Estado
  texto?: string
}>()

const config: Record<Estado, { rotulo: string; classe: string }> = {
  direto: { rotulo: 'Encaixe direto', classe: 'bg-seiji-lo text-seiji' },
  adaptacao: { rotulo: 'Precisa de adaptação', classe: 'bg-ki-lo text-ki-txt' },
  nao_serve: { rotulo: 'Não serve', classe: 'bg-shu-lo text-shu' },
  sem_dados: { rotulo: 'Sem dados', classe: 'bg-surface text-mute' }
}

const atual = computed(() => config[props.estado])
const rotuloExibido = computed(() => props.texto ?? atual.value.rotulo)
</script>

<template>
  <span class="..." :class="atual.classe">{{ rotuloExibido }}</span>
</template>

1. <script setup> não é JavaScript comum

É açúcar sintático compilado pra Composition API. O código vira o corpo de uma função setup() — e essa função roda de novo cada vez que uma instância do componente é criada (cada `SeloCompat` novo na tela tem sua própria execução, suas próprias variáveis).

"The code inside is compiled as the content of the component's setup() function."

— documentação oficial do Vue

2. defineProps — parece a mesma mágica da lição 2, mas não é

Repare: defineProps<{...}>() não tem import em lugar nenhum do arquivo. Isso porque é uma compiler macro — só existe durante a compilação, depois some.

"defineProps and defineEmits are compiler macros only usable inside <script setup>. They do not need to be imported, and are compiled away when <script setup> is processed."

Na lição 2 você viu sql<number> do Drizzle — tipo que não faz nada em runtime, só avisa o TypeScript. defineProps<T>() parece igual na sintaxe, mas não é igual no efeito: o compilador do Vue lê esse tipo e gera configuração de prop de verdade (obrigatória, com validação) que roda em produção.

Duas ferramentas diferentes que usam o mesmo truque visual (<T> genérico) pra coisas completamente diferentes — uma é dica morta, a outra vira código. Vale checar sempre qual é qual antes de assumir.

3. computed — não é uma função normal

atual e rotuloExibido são propriedades computadas cacheadas. Enquanto props.estado não mudar, acessar atual.value de novo não roda a função de novo — devolve o resultado guardado.

"computed properties are cached based on their reactive dependencies. A computed property will only re-evaluate when some of its reactive dependencies have changed."

— documentação oficial do Vue

Repare que rotuloExibido depende de atual.value — um computed usando outro computed encadeado. Se fosse função normal chamada direto no template ({{ calcularRotulo() }}), ela rodaria de novo a cada re-render do componente, mesmo sem nada ter mudado.

Pratique — recupere da memória, não releia

1. defineProps não tem import em nenhum lugar do arquivo. Por quê?
Isso — compiler macro: só existe em tempo de compilação, some do código final.
Não. É especificamente uma compiler macro do <script setup> — nada a ver com import global ou TypeScript genérico.
2. Diferente de sql<T> do Drizzle (lição 2), o defineProps<T> do Vue...
Exato — mesma sintaxe (<T>), efeito oposto: aqui o compilador gera código real de validação de prop.
Não. sql<T> é dica morta pro TypeScript; defineProps<T> gera comportamento real em runtime — são opostos nesse sentido.
3. Por que atual e rotuloExibido usam computed() em vez de função normal chamada no template?
Certo — cache por dependência reativa. Função normal reroda a cada render, computed só quando props.estado muda.
Não. Função normal funcionaria (Vue não proíbe), só que sem cache — recalcularia sempre, sem necessidade.
Quer ver o cache do computed acontecendo? Dá pra colocar um console.log dentro do computed, trocar a prop estado de fora, e observar quando ele realmente roda de novo. Ou qualquer outra dúvida — pergunta direto pro Claude no terminal.

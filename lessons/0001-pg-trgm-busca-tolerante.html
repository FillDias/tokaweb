Por que "VST88" acha a peça certa

como codigo_norm + pg_trgm fazem a busca do TOKA tolerar erro de digitação

Isso aqui não é hipotético — é código que já roda no seu projeto, em server/api/buscar.get.ts. Alguém digita o código da peça errado (VST88C1SS3, devia ser VSTB8C1SS3) e a busca ainda acha a TEIN Flex Z certa, em primeiro lugar, com score 0.571.

Essa lição explica o mecanismo por trás disso, peça por peça.

1. O trigrama

A extensão pg_trgm quebra qualquer string em grupos de 3 caracteres consecutivos — trigramas. Cada palavra ganha dois espaços de prefixo e um de sufixo antes de ser quebrada.

exemplo
cat → " c", " ca", "cat", "at "

"A trigram is a group of three consecutive characters taken from a string. We can measure the similarity of two strings by counting the number of trigrams they share."

— documentação oficial do pg_trgm

2. similarity() e o operador %

similarity(a, b) conta quantos trigramas a e b têm em comum e devolve um número de 0 (nada em comum) a 1 (idênticas). O operador % é o atalho: a % b é verdadeiro quando similarity(a, b) passa de um limiar (threshold).

O threshold é o parâmetro pg_trgm.similarity_threshold, padrão 0.3. O TOKA não sobrescreve esse valor em nenhum lugar — então a busca usa o padrão do Postgres.

No projeto, isso vira a query de server/api/buscar.get.ts: 

.where(sql`${peca.codigoNorm} % ${termo}`)
.orderBy(sql`similarity(${peca.codigoNorm}, ${termo}) DESC`)

3. Por que existe codigo_norm

Repare: a query compara contra codigo_norm, não contra codigo. A pergunta natural é "isso é porque o pg_trgm não lida com hífen?" — e a resposta é não: a própria documentação diz que o pg_trgm já ignora pontuação ao montar os trigramas. O motivo real é outro: codigo_norm deixa tudo maiúsculo e sem hífen pra que toda consulta — a busca tolerante e a busca exata do GET /api/peca/[codigo] — bata contra a mesma forma canônica, não importa como o usuário digitou.

no banco — server/database/schema.ts
codigo_norm text GENERATED ALWAYS AS
  (upper(regexp_replace(codigo, '[^a-zA-Z0-9]', '', 'g'))) STORED

Coluna gerada — o Postgres calcula sozinho toda vez que codigo muda. Ninguém escreve em codigo_norm direto.

4. O índice

Sem índice, % ainda funciona — só que varrendo a tabela inteira toda vez. O índice GIN com gin_trgm_ops guarda os trigramas de forma buscável: 

CREATE INDEX peca_codigo_trgm ON peca
  USING gin (codigo_norm gin_trgm_ops);

Pratique — recupere da memória, não releia

1. Por que codigo_norm existe, em vez de comparar direto contra codigo?
Isso — o pg_trgm já ignora pontuação sozinho. codigo_norm existe pra normalizar maiúscula/hífen de forma consistente em toda consulta, não só na busca tolerante.
Não é isso. Releia a seção 3 — a pista está em "toda consulta", não só a busca por similaridade.
2. O operador % em codigo_norm % 'VST88C1SS3' compara a similaridade contra o quê?
Exato — pg_trgm.similarity_threshold, padrão 0.3 no TOKA (nunca foi alterado).
Não. É um valor fixo e configurável: pg_trgm.similarity_threshold.
3. Sem o índice GIN em codigo_norm, o que muda numa busca?
Certo — índice é sobre desempenho, não sobre correção. Sem ele, o Postgres varre a tabela inteira.
Não. O índice acelera, mas a busca já funciona corretamente sem ele — só fica lenta em tabela grande.
